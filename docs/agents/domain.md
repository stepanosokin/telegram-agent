# Domain docs

This repo uses a single context. Read `GLOSSARY.md` at the repo root and relevant decisions in `docs/adr/` before exploring the codebase. If either path is absent, continue. Create domain documentation through `domain-modeling` when a term or decision is settled.

Use glossary terms in tickets, specs, and test names. Bring missing terms to `domain-modeling`. When a proposal conflicts with an existing ADR, cite the decision and explain the conflict.
